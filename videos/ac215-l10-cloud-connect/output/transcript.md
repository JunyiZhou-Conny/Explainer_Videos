## 11:15 — ADC: from key file to bearer token
So what failed? The loader's Google client, like the API's, is built from a project and a location, nothing else. No code in this repo opens the key file; a library does, by a convention called application default credentials, or ADC.
ADC looks in three places, in order. First, the file named by the Google application credentials variable: a service account key, as in this tutorial. Second, a login file the gcloud tool writes for you, as a person. Third, the metadata server, when your code runs inside Google's cloud. ADC moves to the next place only when the one before is not set. Inside these containers, only the first place exists.
The library writes a small note, a JSON web token, and signs it with your private key. It sends that note to Google's token desk, at the address in your key file. Google holds the matching public key, so it checks your signature without ever seeing the private one. Back comes an access token, valid for about an hour. That token rides on every request as a bearer header. Your private key never leaves your machine; only the short-lived ticket travels.
When the hour runs out, the library gets a new one. The lecture's OAuth diagram ends at this same desk, minus the consent screen: no person is there.
Here is ADC caught in the act. With slash secrets empty, an extra one-line Python check asks ADC who we are. The variable is set, so ADC opens that path, finds no file, and stops right there, with the same error. A wrong path never falls back to the other two places. With your key in place, it names your service account instead.
One common mix-up: setting that variable on your Mac authenticates nothing inside a container, where the path must exist. That is why the scripts set a container path, and mount the host folder separately.

## 13:19 — IAM: may this identity do this, here?
Authentication proved who your code is. Authorization decides what it may do, and where. Google calls this IAM: a grid of identities, roles, and resources. Your service account holds the Gemini user role in your project, and that green cell does the work. Storage Admin sits beside it, granted but never used by this app.
Three requests test three cells. IAM checks the resource the request names; for an embedding, the client writes that name from your project variable. An embedding in your own project is allowed. The same call with the script's unedited default project is refused with a 403, because your account has no role there. That is why you edit both scripts. The third arrow waits for part 2.
A default credentials error, or a 401, means no valid token: check the path, the mount, and the file name. A 403 means authentication worked, but authorization failed. The cause: a missing role, the wrong project, or an API that is not enabled.
That last cause is a small gap: no README here says to enable the Vertex AI API. If you never did, the 403 says so, and one extra gcloud command fixes it.
Something to ponder. Your key works for embeddings. Now you paste the instructor's endpoint, which begins with projects and a long number. Which part decides whose IAM is checked: the project variable, the project inside your key, or the endpoint path?
The path. Not the key's project: that only says where the badge was issued. Not the variable: the endpoint path already names a project, and that name wins. It is someone else's project, where your account has no role, so it is a 403; part 2 draws it.

## 17:46 — A name is not localhost
Part 2 starts with addresses; every command in this scene is an extra. The loader dials the database by name: llm-rag-chromadb, port 8000. Your browser will ring localhost 8000, through a door in the laptop wall. One server, two addresses. Why can they not swap?
Each container is its own house, with its own localhost. Inside a container, localhost means that container. Names work through Docker DNS, a phone book on each street. IP addresses change when containers restart, but names do not. This extra inspect shows the API's IP address on its street. Yours will differ, which is the point: dial names, not IP addresses. And your laptop is not on any street, so it has no phone book: that name means nothing to your browser.
Now the proof. From inside the API container, ask for the database by name. The answer: name or service not known. The API's street has no entry for that name.

## 22:22 — The browser is the integrator
This setting, baked into the JavaScript your browser downloads, gives the page the API's address. So it must be one your browser can reach: localhost 9000, never a container name.

Step 3, the chat, has a gold tag: one embedding and one Gemini answer per question. Pause, pick a collection, and ask one. On your machine, it makes three calls. Call one: the API asks Google, and 256 numbers come back.
Call two asks the database for the 10 nearest chunks. An origin is scheme, host and port, so a page from 3200 calling 8000 crosses origins.
By default, a browser will not let a page see replies from another origin. A server can allow named origins; that is CORS, and it keeps other websites from reading your local services. So the browser first sends a preflight with the page's origin. The database checks its guest list, the course's site and localhost 3200, and returns a pass, or nothing. Your browser is the bouncer: no pass, no query.
Call three sends the question and ten chunks to the API, and the answer returns. An extra curl writes its own Origin header. Both preflights get 200 OK, but only 3200 gets a pass; to a browser, no pass is a refusal.
Something to ponder. You republish the frontend on port 3300. Which of the three calls fails, and does curl care?
Call one works: the API allows any origin. Call two never leaves the browser. Call three waits for it, so it is never sent. And curl ignores it all. CORS is enforced by the browser, configured by the server, and keyed on the page's origin. Even 127.0.0.1, port 3200, is a different origin from localhost 3200, so open the app at localhost.
Look for an answer and ten references, with book, author and distance. Last thought: CORS decides which page may see a reply; nothing here decides who may call. An unprotected AI endpoint, spending your key, is running on your laptop.

This app never calls a bucket, which is why Storage Admin sat gray; next lecture uses one. The lecture gives four rules. Grant object admin, not full admin. Keep buckets private. Prefix their globally unique names. And delete what you no longer need, because storage and downloads cost money.
